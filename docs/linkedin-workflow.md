# LinkedIn email and job review workflow

Capture a full local description for a canonical held job, then run the reviewed job through SQLite, a stable Discord review thread, explained fit, an approved-evidence resume draft and exact PDF attachment. Start with the synthetic local demo, inspect its page images, then retain the database and private artifacts for restart. Gmail/account connection and real Discord delivery require a separate authorized test.

## Local full-description review (PR1)

Alerts are leads/snippets only, including previously persisted records. No automated LinkedIn/Indeed page capture, login or challenge bypass is authorized. Synthetic HTML is consumed by the offline classifier only. Employer ATS detail APIs are later PRs.

1. Use `description-template --db PRIVATE_DB --lead-id HELD_ID --output PRIVATE_JSON` with the built CLI (`node dist/src/cli.js`). The output is a new mode-0600 JSON file, prefilled from the actual canonical job; existing files are never overwritten.
2. Paste the entire employer description in `body`. Review title/company/location/source/sourceURL, capture time and optional exact `requirements` quotes. Retain `postingFingerprint`; a changed job requires a fresh template. Set `fullDescriptionConfirmed: true` only after reviewing the entire body. `byteCutoff` must stay false unless the capture was cut off.
3. Run `description-capture --db PRIVATE_DB --input PRIVATE_JSON`. It persists an immutable local version with classification/provenance and prints metadata without body or requirement quotes. Unconfirmed input is rejected. Empty body, ellipsis, show/load-more and byte cutoffs remain `partial`; unknown/missing sections or HTML paste stays `layout_unknown`; auth walls, challenges and expired postings stay `needs_login`, `blocked` and `expired`. Confirmation cannot override those holds. Plain full text must contain responsibilities/about-role and requirements/qualifications, plus a substantial body; conservative false holds require a verified fresh paste, not a flag bypass.
4. Inspect `description-state --db PRIVATE_DB --lead-id HELD_ID`. History and old artifacts remain immutable. Replaying a historical version never moves the current pointer backwards. New complete capture invalidates old work/eligibility and requires a new explicit eligibility review. Changed posting facts invalidate the capture; a later partial capture invalidates prior preparation/model planning/attachment.
5. Use the existing `linkedin-eligibility` and `linkedin-work` flow with approved private evidence. Work IDs and prepared input hashes bind the exact current description version. All preparation, Codex planning and attachment admission recheck persisted completeness and current version; stale legacy draft fields cannot create a resume. Pure PDF helpers accept approved prepared data, not job descriptions.

Keep the SQLite DB, paste files, candidate inputs, PDFs and receipts in ignored `data/` or a private external directory. Real Discord attachments are disabled at both the workflow and actual REST transport boundary, including queued historical work. No resume bytes are read for a real attachment attempt and no upload request is made. Local fixture attachment tests still preserve exact bytes; a fixture receipt is never a real send.

`source-gate --db PRIVATE_DB` displays durable defaults: global killed, LinkedIn killed, Indeed killed, both budgets zero. The optional `--source global|linkedin|indeed --killed true|false` updates task-domain state. Kills survive process restart; budget zero cannot be changed by clearing kills or enabling a legacy alert. Existing Indeed search sync checks before creating its fetcher, and direct browser-adapter use refuses through the same zero-budget consumer before credentials/browser activity. This creates no service or scheduler.

For reproducible synthetic CLI proof, build and run `node scripts/job-description-demo.mjs --output-dir PRIVATE_EMPTY_DIR --phase prepare --portfolio-root PINNED_ASSET_DIR`, inspect `previewPath`, then run `--phase verify --approve-visual` with the same paths. Verify covers six hold types, explicit acceptance, actual fit/one-page PDF, exact local fixture bytes, second version/history/replay/restart, stale work refusal and partial invalidation. `--phase state` displays final metadata; `--plain` removes decorative glyphs. The script accepts no real candidate/description inputs. Receipts/logs remain local. Only the fixture verify phase uses visual approval; never approve an uninspected real page.

Morning review is paste flow/source defaults; later supply employer URLs and initial ATS tenants. Full design stays with Kevin. PR2 Greenhouse/broker, PR3 matching/reposts/agency handling, PR4 exact-quote requirement/evidence mapping, and PR5 more ATS adapters remain deferred until PR1 is CI green/pre-merge. Gmail-history work is parked separately and not bundled. See [PR1 decision plan](../plans/job-description-pr1.md).

## What this implementation proves

| Stage | Current evidence | Boundary |
| --- | --- | --- |
| LinkedIn intake | Normalized JSON plus trusted captured Gmail full/raw MIME and labeled HTML parsing | Unknown/unlabeled layouts held; no live Gmail history consumer or automatic auth verifier |

## Captured connection demo

Use `node scripts/linkedin-demo.mjs --output-dir data/linkedin-connections --phase connections` for the complete synthetic connection handoff. It builds a captured Gmail JSON message plus **synthetic-only** trusted context, ingests four jobs, records an authorized note against the original persisted thread, prepares two eligible jobs, and writes immutable private Codex plans. The result reports zero model calls/production sends and `blocked_cli_isolation_unverified`. Continue with the existing prepare/render and visual-review/attach demo phases if desired.

New CLI seams are `gmail-intake --email-file CAPTURE_JSON --trusted-context CONTEXT_JSON --verified-handoff --transport fixture --journal PRIVATE_JSON`, `discord-review --interaction-file CAPTURE_JSON --review-config ALLOWLIST_JSON --verified-handoff`, and `codex-resume-plan --work-id ID --private-dir DIR`, all with the same `--db`.

Gmail context is separate trusted verifier output: `{verifier:"local-gmail",messageId,sender,authenticated:true,evidenceId,payloadSha256}`. The digest is SHA-256 of `JSON.stringify(capture)` and binds the serialized capture content and identity, rather than the original JSON file's whitespace. It is not generated from mail headers. Supported captures include base64url Gmail multipart, bounded raw MIME/base64/quoted-printable and labeled HTML with explicit job fields. UTF-8 only; missing/ambiguous fields and unsupported layouts produce durable SQLite intake holds with reasons. Correct verification/parsing can resolve the same captured-version hold. No Gmail API/account/authentication verifier is invoked.

Discord review requires separate configured target/user/parent-channel/thread allowlists plus authenticated interaction metadata containing the original thread/root-message IDs. The handler resolves the job from persisted delivery state; payload lead IDs are not authority. `applied_manually` requires `manualApplicationConfirmed:true`, and actor/interaction provenance is stored atomically with state changes. Interaction admission takes the SQLite write lock in that same transaction, so two independent processes cannot both apply one interaction. A replay returns `replayed_interaction` without another state/audit write; audit failure rolls the whole action back. Context-free local operator actions remain repeatable. A JSON flag is not cryptographic authentication; a live signature/socket consumer is still required.

Codex planning validates current eligibility and exact handoff/prepared hashes, job version and thread. Its plan remains private. The module and CLI expose **planning only**; no injected runner, model invocation or execution-receipt writer is available. Installed Codex help did not establish a no-tools/no-network boundary sufficient for untrusted posting text, so the plan retains `blocked_cli_isolation_unverified`. The existing `receiptPath` field remains reserved metadata used to locate CLI plan output; planning does not create, rewrite or remove receipt files. Preserve any private historical receipts.

## Actual CLI and private inputs

`node dist/src/cli.js help` prints the supported commands and flags. JSON goes to stdout; progress goes to stderr every five seconds during slow work. `--plain` removes decorative glyphs. No secrets are accepted on the command line.

- `linkedin-intake`: requires `--email-file`, `--transport`, and either `--fixture` or `--verified-handoff`; optionally selects `--db`.
- `linkedin-deliver`: drains/reconciles previously persisted intake without the original email file.
- `linkedin-state`: displays persisted source versions, delivery state and versioned job work.
- `linkedin-eligibility`: requires `--lead-id`, `--status eligible|ineligible|needs_review` and `--note`. An eligible decision means the operator confirmed **all** hard requirements, including authorization, for this exact posting version.
- `linkedin-work`: processes every eligible job, with no minimum score, role exclusion or top-N cutoff. Use private `--candidate` and `--evidence` JSON paths; `--private-dir` controls outputs. Without `--render`, it stops at prepared inputs. Add `--render --portfolio-root` to run the private PDF adapter. Missing/invalid inputs remain durable blocked work.
- `linkedin-attach`: requires `--work-id`, exact `--sha256`, `--approve-visual` and `--portfolio-root`. It revalidates captured bytes and current eligibility before attachment. A validation failure is persisted; an uncertain send must reconcile before another write.

Every command uses the same `--db`. A fixture transport requires `--transport fixture --journal PRIVATE_JSON`. Private candidate JSON is `{ "name": "Alex Example", "email": "alex@example.test" }` for the synthetic example. Approved evidence is an array of `{ "id": "synthetic-python", "claim": "Built **Python** validation fixtures.", "skills": ["python"], "source": "synthetic://approved/commit", "approved": true }`. Real evidence must come from verified contributions, not posting text or an inferred directory owner. Approval flags are a trusted operator handoff, not an authorship verifier.

## Delivery recovery

SQLite is canonical; the Discord journal/remote channel is a projection. Message replays are transactional. Different posting URLs stay separate even with identical titles/companies. Older observations remain in the message version ledger but cannot replace newer posting content. Equal observation timestamps are not a robust external ordering signal; controlled handoffs should preserve accurate provider receive times. The existing Indeed/legacy fixture dedupe policy is unchanged.

Initial sends have a 60-second per-item lease; job work has a five-minute lease. A crashed write becomes reconciliation-required after its lease expires. Readback looks for the stable marker authored by the configured bot, and validates thread/attachment receipts. A bounded 100-message history read cannot prove absence: a missing match stays uncertain. Do not clear uncertain state or resubmit blindly. A later matching readback resumes the same job/thread. Missing permissions, deleted/archived threads or unresolved ambiguity require operator investigation.

429 timing starts when the response arrives, and target backoff is persisted. Readback throttling preserves uncertainty across retries. Corrected location holds can resume, while a current rejection or duplicate hold stops pending delivery, expired-send recovery and new thread creation after readback. Completed receipts are preserved. Posting versions include exact parsed remote-eligibility text, seniority, employment type, office location and compensation fields as well as title, company, location, work model, description, skills and location decision. A change requires a new eligibility decision and keeps prior work for audit; existing work made with the older fingerprint also requires renewed review after upgrading. Audited operator rejection and duplicate holds, along with manual resume selection, are retained across unchanged and changed posting refreshes, and the packet is rebuilt from the final state. A hold blocks alerts, enrichment, attachment and prepared Codex dispatch even when prior eligibility remains approved; the operator must change the review status before admission can resume. See the [refresh regressions](../tests/linkedin-refresh.test.ts).

Transient GET network, server and unreadable-JSON failures use the existing retry/backoff state. A failed initial thread lookup or fit/PDF preflight does not imply an unknown write. If an earlier POST was already uncertain, a failed readback preserves that reconciliation requirement. POST interruption/server/unreadable-receipt outcomes remain uncertain; genuine permission blocks remain terminal.

Remote-eligibility text is stored in the nullable `remote_eligibility_raw` column, added automatically when opening an older database. Historical missing text remains unknown until a new observation; no eligibility classification or inferred backfill is introduced. A newer LinkedIn observation replaces the exact parsed text, including removal. Legacy merged observations retain the most recently supplied text when later metadata omits it.

Work admission is checked after claim and again after awaited fit delivery/readback, PDF validation and rendering, before new preparation or artifact publication. Fit transport rechecks synchronously after thread lookup, immediately before POST. Real PDF workflow/transport refuse before byte loading or any request; fixture PDF admission still rechecks. Revocation or changed source facts block further writes while retaining prior inputs and known/uncertain receipts; a returned receipt is recorded even when its send or readback overlaps revocation. Validation-time attachment denial fails before creating a delivery attempt or replacing visual approval.

A known local admission denial before POST preserves the previous fit/PDF delivery record exactly, including an absent record or a definite retry. Restore explicit eligibility for the unchanged posting and repeat the same work/attachment command to resume; the inputs remain immutable. Actual transport permission blocks stay blocked, and uncertain attempts still require matching readback. An already issued remote request may finish after revocation; its returned receipt is retained rather than claiming cancellation.

Initial alert/thread admission uses the existing recoverable `held` state. If an operator rejects a job or marks it duplicate during root/thread readback, the next new write stops while known root receipts, retry timing and reconciliation requirements remain stored. After explicit operator reapproval, drain the same target again: it resumes from the known root and reconciles uncertain thread attempts before creating anything. Genuine transport blocks remain terminal even across a queued operator hold and reapproval; older `blocked` records are not automatically reclassified.

Fixture journal mutations share a SQLite immediate transaction using a private adjacent `.lock.sqlite` file. Concurrent alert, thread, fit and attachment writes preserve successful receipts; repeated attachment keys retain the original bytes. SQLite releases the lock when a process exits. Keep the private run directory together when resuming or restoring; the JSON journal remains the receipt record. Lock contention errors flow through the existing uncertainty handling.

The [Discord message API](https://docs.discord.com/developers/resources/message) only deduplicates an enforced nonce over a short recent window; this implementation therefore retains local receipts/reconciliation rather than claiming exactly-once delivery. It disables all generated mentions, suppresses previews and uses [documented message threads](https://docs.discord.com/developers/resources/channel). [Rate-limit responses](https://docs.discord.com/developers/topics/rate-limits) control retry timing. Real PDF uploads are disabled for this rollout; status/local references never count as PDF delivery. Fixture attachments remain local.
